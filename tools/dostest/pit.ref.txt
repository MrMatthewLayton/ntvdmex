# p_pit reference -- the 8254 as software can observe it
#
# Source: tools/dostest/p_pit.asm on genuine MS-DOS 6.22 (the msdos622 oracle),
# 2026-09-23. Every case is deterministic ON A HOST THAT IMPLEMENTS THE SURFACE:
# none emits a counter VALUE, only structure that is the same on any machine on
# any day.
#
# ⚠ THAT GUARANTEE IS CONDITIONAL AND I FIRST WROTE IT AS ABSOLUTE. The three
#   read-back cases are deterministic only BECAUSE a status byte is stable. On a
#   host that ignores the Read-Back Command the following IN returns a live
#   COUNT, so the value varies run to run -- which is what our rdback.st0 does.
#   The verdict (MISMATCH) is stable; the mismatching VALUE is not, and recording
#   one run's figure as though it were fixed would have been a stale artefact.
#
# ⚠ PROVISIONAL AGAINST SeaBIOS for the one BIOS-dependent row (st0). The chip
#   rows are chip behaviour and should hold anywhere; re-ask on PCem.

== pit.ch1.counting        0x0001   two latched reads of counter 1 differ: it is running
== pit.ch2.counting        0x0001   same for counter 2, gated on via port 61h bit 0
== pit.rdback.st0          0x0034   Read-Back status of counter 0, bits 5:0
                                    = lo/hi access, MODE 2, binary
                                    ⚠ NOT mode 3 -- see docs/ref/pit.md §6. The
                                    mode is a BIOS choice; this is SeaBIOS's.
== pit.rdback.st2          0x0030   counter 2 as this probe programmed it:
                                    lo/hi, mode 0, binary
== pit.mode6.readback      0x000C   mode field after programming 110: hardware
                                    reports the bits AS PROGRAMMED (6), it does
                                    NOT normalise to 2. Read-back fidelity only --
                                    it does not prove the aliasing BEHAVIOUR.
== pit.bcd.valid           0x0000   ⛔ BLOCKED ON PCem -- NOT a verified row.
                                    The first version of this case took ONE
                                    sample, and a BINARY counter passes that
                                    whenever its four nibbles happen to be <= 9
                                    (~1 value in 6). It duly reported 0x0001 on
                                    both hosts while NEITHER implements BCD.
                                    Strengthened to 16 spread samples, the ORACLE
                                    fails it too: QEMU's PIT does not model BCD
                                    either. So both hosts now answer 0x0000 and
                                    dosdiff calls it AGREE -- which is AGREEMENT
                                    ON ABSENCE, not verification.
                                    ⇒ Needs a real chip model. Same queue as the
                                    VGA modes 04/06 row and the DAC pixel mask.
== pit.61h.bit5.toggles    0x0001   counter 2's OUT pin, read at port 61h bit 5,
                                    changes state within a bounded poll

# ── NTVDMEX, host 77b9b0bd, same day: 7 of 7 MISMATCH ────────────────────────
#   ch1.counting      0x0000   port 41h returns 0xFF -> two identical reads
#   ch2.counting      0x0000   port 42h returns 0xFF -> likewise
#   rdback.st0      ⚠VARIES   read-back swallowed; the 40h read returned a LIVE
#                              COUNT, not a status byte -- 0x21 on one run, 0x30
#                              on the next. The VARIANCE IS ITSELF THE DIAGNOSIS:
#                              a status byte cannot change between two identical
#                              runs, a counter must.
#   rdback.st2        0x003F   0xFF masked to bits 5:0
#   mode6.readback    0x000E   0xFF masked to the mode field
#   bcd.valid         0x0000   the BCD control bit is stored and never consumed
#                              (vdd_pit.c:99) -- but see above: the ORACLE cannot
#                              currently prove what the right answer is.
#   61h.bit5.toggles  0x0000   bit 5 echoes what was written, never the OUT pin
#
# ★ Every one of these was predicted from the CODE in docs/inventory/pit.md
#   before the probe existed, and the probe confirmed all seven independently.
