## Partial M2.4 validation (recovered from a pre-crash run; target.txt = mem.exe)
The recovered `C:\ntvdmex\vdmhost.log` (from an **older** binary that had `AH=4A` but not `44/63`)
shows real `mem.exe` running through our host:
- `target.txt` override loaded `C:\WINDOWS\system32\mem.exe` (0x996a bytes); MZ loader parsed it
  (`hdr=0x200 img=0x976a relocs=0 CS:IP=0xa6d:0x10 SS:SP=0xadf:0x80`).
- **`INT21 AH=4A resize seg=0x100 -> 0x174e` succeeded (no CF)** — a real Microsoft DOS binary
  shrank its initial allocation through our M2.4 resize handler. First M2.4 evidence on real code.
- Then `AH=44h` (IOCTL, ~10x) and `AH=63h` (DBCS, ~6x) logged **`unhandled`** → that run used the
  pre-44/63 binary. mem.exe gave `==> DOS OUTPUT: [Parse Error 1]` and terminated `AH=4Ch AL=1`.

## [FACT] The VM dev loop is now the bottleneck — flaky/slow telnet comms
- QEMU host-port forward (`localhost:2323`) **accepts the TCP connection the instant QEMU starts**,
  before the guest telnet service is up — so `nc -z 2323` is a false "ready". Must do a real
  `xp.py` login to know the guest is alive.
- `xp.py` logins are **increasingly slow and intermittently hang** (observed a multi-minute stall
  with 0 bytes returned, then the full output arrived at once on kill). XP telnet allows few
  concurrent sessions and refuses rapid reconnects; a not-fully-closed prior session compounds it.
- Net effect: each test round (push → set target → trigger → read log) costs minutes and sometimes
  needs a kill+retry. This is now slower than the code changes themselves.
- **Mitigations to consider next session:** keep one long-lived telnet session instead of
  reconnecting per command; or drive via a guest-side batch that runs the whole loop and writes a
  single result file; or use the QMP socket / a file-drop channel instead of telnet for the
  push+trigger+collect cycle.
