# 2026-06-09 — mode-12h tiered interpreter, the per-pixel wall, INKEY$/XCHG fixes

## Summary

All 10 QuickBASIC demos now **run**. The remaining question from 2026-06-08 — "make the 12h pixel
demos fast" — turned out to hit a **fundamental wall**, documented below. Net result: keep the
interpreter (it fixed real bugs + helps short loops), accept 12h pixel-plot as correct-but-slow, stop
adding interpreter opcodes.

## What shipped

- **Bounded flags-accurate 8086 interpreter** (`src/host/v86interp.h`), fully memory-abstracted (code
  fetch + data via `imem_r8/imem_w8`, port I/O via `iio_in/iio_out`) so it's **unit-testable off-VM**:
  `tools/dostest/interp_test.c`, **63 checks** over a flat memory array — exact flags for the ALU group,
  ModRM + seg-override + BP-default-SS, MOV (incl. Sreg/moffs/imm), REP STOS/MOVS/LODS (fwd + DF back),
  XCHG, PUSH/POP (gp + seg), IN/OUT via stubbed bus, CALL/RET (near + indirect), Jcc/JMP/LOOP, shifts/
  rotates, LEA, and two full PAINT read-scan loops.
- **Tiered execution** (`host_interp()` + service loop in `src/host/main.c`): default = single-instruction
  **device** emulation (CPU runs the loop on silicon); opt-in **batching interpreter** only on a detected
  mode-12h **trap-storm** (same tight PC window faulting repeatedly). Storm detection lives in the service
  loop so it covers **port faults** (the dominant cost) as well as A0000 memory faults.
- **Two correctness fixes:**
  - **`XCHG ES:[DI],AL`** (opcode 0x86) — QB's mode-12h pixel-store. The interpreter didn't model it, so
    it bailed → stop dump → engine terminated (the "filled but frozen, won't close" window). Added XCHG.
  - **INKEY$ phantom key** — QB's `INKEY$` uses INT 16h enhanced fns **AH=10h/11h**, which fell into a
    `default: ZF=0` in `vdd_input.c` → reported a phantom keystroke → `DO WHILE INKEY$ = ""` exited
    instantly and **BLIT.EXE drew nothing**. Implemented 10h/11h (mirror 00h/01h) + made the default
    report "no key"; host now blocks on AH=10h like AH=00h. Input battery **15 → 20**.

## The wall (the important finding)

QuickBasic's runtime plots **one pixel at a time** — ~50 instructions **plus a per-pixel VGA register
`OUT`** (it reprograms the Graphics Controller bit-mask for every pixel). Cost per pixel:

- **Real CPU + trap-per-access:** ~50 native instr (fast) **+ 2 kernel round-trips** (the OUT + the XCHG,
  ~µs each) → round-trips dominate.
- **Batched interpreter:** 0 round-trips, but the ~50 instr/pixel now run **interpreted** (~50–100 ns
  each) → ~same µs/pixel.

So batching just trades round-trips for interpretation — **roughly equal** for QB's fat routine — and a
~307K-pixel fill is ~1 s either way. Confirmed empirically: as opcodes were added the batch factor went
**5 → 23 → ~50** (peaks 757) with **no change in wall-clock speed**. Adding `LES`/`LDS` would batch
further but cannot break the wall, because the wall is "QB does ~50 ops/pixel and an interpreter is slow
per op." Your original instinct (don't interpret) is vindicated: the thing being interpreted is itself
enormous per pixel.

**Decision:** stop the opcode climb; keep the interpreter; document; move on. Linear modes (13h/VESA)
are unaffected — the CPU writes pixels straight into a flat aperture, fast.

## VM-harness gotchas learned today

- A demo that **loops** (BUBBLES) leaves `ntvdmhost.exe` running → **locks the file** → RUNTEST's next
  copy fails ("being used by another process") and silently runs the *old* host. Close the Luna window
  (or reset the VM) before re-staging.
- `system_reset` via QMP reboots cleanly and keeps the CD mounted, but **occasionally drops QEMU** —
  relaunch `scripts/xp-vm.sh run` if `pgrep -x qemu-system-x86_64` shows it gone.
- Closing Luna windows via QMP `send-key` is flaky; faster to ask the user to close them.
- `screendump` occasionally returns a low-res frame during a mode-12h present; just re-shoot.
