## What landed (the graphics stack, slices 8–on)
- **VESA VBE 2.0, banked (`328b9af`):** INT 10h AX=4F00/01/02/03/05; modes 0x100/0x101/0x103; a
  0x80000 VRAM window + `vesa_bank` select in the video VDD. `vesademo.com` (nasm) drew a smooth
  scrolling gradient.
- **Mode 12h, 640×480×16 PLANAR (`105d52a`, `a21d2be`) — the hardest piece:** A0000 is trapped via
  `VirtualProtect(PAGE_NOACCESS)` (`a000_protect()`) whenever mode 12h is active; the faulting store is
  decoded in `host_try_mem()` and run through `vga_planar_write` — VGA **write modes 0–3**, Sequencer
  **Map Mask** (3C4/5), Graphics Controller **set/reset + enable-SR + function/rotate + bit-mask + read
  map** (3CE/F), and the **4 latches** — into 4 plane buffers; `render_planar` combines them to the
  framebuffer. `vga12.com` drew the 16 horizontal colour bands. **Decoder gap (logged for follow-up):**
  only STOSB/STOSW (REP) stores are decoded; arbitrary MOV/ModRM stores (QBasic SCREEN 12) are TODO.
- **13h/VESA "blue for 2–3s" stall fixed (`6e124ad`):** the cause was a ~768-OUT DAC palette loop,
  each OUT a slow V86 I/O trap (and earlier made worse by per-trap log-file flushing — also removed).
  Fix: the demos set the whole palette in **one** INT 10h AH=10/AL=12 call.
- **Windowed presentation rebuilt (`67e6435`, `693d734`, `cbfc5b3`):** moved windowed off
  DirectDraw-to-primary (cursor flicker) to **GDI `StretchDIBits`**, then to a **double-buffer
  snapshot** (`_snapshot()` under the bus lock, `_present()` outside it) + **`WaitForVerticalBlank`** +
  **hide the cursor over the client area**. This is as tear-free as XP's desktop allows — there is no
  compositor, so the genuinely tear-free path is **exclusive fullscreen DirectDraw flip** (kept for
  Alt+Enter). Explained to the user why GDI is used in window mode and what vsync/double-buffer buy.
- **Host chrome (`67e6435`, `a21d2be`, Luna manifest):** full **menu-bar scaffold**
  (File/Edit/CPU/Display/Audio/Input/Drive/Capture/Debug/Help — unwired entries → `IDM_STUB`; wired
  Exit / Fullscreen / Show-menu-bar / About), a **native comctl32 status bar** (shows the running
  program), and the **Common-Controls 6.0 manifest** (`res/ntvdmhost.rc` → `ntvdmex.manifest`) so the
  window frame is Luna-themed. (XP can't theme the menu bar itself — that's a Vista+ feature.)
- **Animated demos (`8aa2c88`) via nasm:** `tools/dostest/{demo13,demo12,demovesa}.asm` +
  `make-demos.sh` → `vgademo`/`vga12`/`vesademo`.com — each animates and exits on a keypress, run loop
  goes until the window closes. They confirmed all three modes animate correctly on the real CPU.

## FIRST REAL QUICKBASIC APP RENDERS (VM-CONFIRMED, 2026-06-08)
Diagnosed the demos in the VM and closed the first two DOS-layer gaps. **`PALETTE.EXE` (QuickBASIC
4.5, SCREEN 13) now renders its colour-ladder graphics in the Luna window on the real CPU** — the
first real DOS application running end-to-end through NTVDMEX.

Two gaps, found by reading `ntvdmhost.log` (drive the VM via `scripts/qmp.py`):
1. **INT 21h AH=06 (Direct Console I/O)** was unhandled (`7bd40a1`). QuickBASIC routes *all* console
   output + keyboard polling through AH=06, so every screen write was dropped → black window and a
   spin. Implemented: DL=FF → non-blocking read (AL=char, ZF per availability); else → output the
   char. Also AH=2A/2C date/time (RANDOMIZE TIMER), AH=0B status, AH=2B/2D. **VM-confirmed:** text
   then rendered, but PALETTE hit a QB **"Illegal function call"** (error 5).
2. **INT 10h VGA capability queries** (`8d88339`). A new INT 10h call-trace in the host showed QB's
   `SCREEN` statement probes the adapter via **AH=1B** (Get Functionality/State Info), **AH=12**
   (Alternate Select), **AH=1A** (Display Combination), **AH=11/30** (font) — all hit the video VDD's
   no-op default → garbage → QB decided mode 13h was unsupported and raised error 5 (it never even
   issued AH=00 AL=13). Implemented proper VGA-BIOS responses: AH=1B returns AL=1B + a 64-byte state
   block with a 16-byte static functionality table (kept in the block's reserved tail at 0x2E so we
   never overrun the caller's buffer) advertising modes 0..0x1F; AH=1A→VGA colour; AH=12 BL=10h→
   256K/colour; AH=11/30→text metrics. **VM-confirmed: PALETTE now sets SCREEN 13 and draws.**

Status by demo class now: **SCREEN 13** (PALETTE ✓, expect CAVE/GFXCOPY) render via the linear A0000
path; **text** (VS87) should render via AH=06; **SCREEN 12** demos (BLIT/BOUNCEBX/BUBBLES/MATRIX_1/2)
now *run without the QB error* (the SCREEN-12 query path is accepted) but paint nothing yet — they
need the **mode-12h MOV-store decoder** (the host's `host_try_mem()` only decodes STOSB/STOSW; QB uses
MOV stores). That + **INT 33h mouse** (MOUSE.EXE) are the next items.

**Root cause for the 12h pixel demos = performance, not correctness.** mode 12h traps every A0000
write (`PAGE_NOACCESS`) → a #GP fault + full V86 round-trip *per pixel*. QB's `PAINT`/`LINE BF`
fill pixel-by-pixel (not REP STOS, which we already batch), so a full-screen fill is ~307K round-trips
= many seconds; the demo never reaches its animation. The MOV-store decoder is correct (the background
*does* paint). 13h is fast (linear, no trap); 12h **text** is fast (glyphs render in-engine via
`glyph_12h`, no per-pixel trap). **Next:** a fill-loop fast path — when an A0000 write faults,
single-step the guest's inner write loop in the host (store + pointer-advance + branch) until it
leaves A0000, so a fill costs one trap instead of one-per-pixel. Sizable (a mini fill-loop
interpreter). Plus **INT 33h mouse** for MOUSE (needed regardless, but MOUSE also needs the perf fix).
BLIT/BOUNCEBX source not yet available (would confirm their exact fill path).

## INT 33h mouse + the fill-loop diagnosis (2026-06-08, later)
- **INT 33h mouse** (`972259f`): seeded as a BOP stub (DOS_HDLR_SEG:0x30) + routed in the service
  loop; UI thread tracks the guest mouse from WM_MOUSEMOVE/buttons (client→frame coords, interlocked
  globals). Functions 00/01/02/03/04/05/06/0B. MOUSE.EXE no longer hits an unhandled INT 33h vector,
  but it's a SCREEN-12 pixel demo so it's still gated by the perf issue below.
- **Fill-loop diagnosis (the input for the fast path).** Instrumented `host_try_mem()` to dump 16 code
  bytes at each A0000 fault and ran BUBBLES. Its `PAINT (0,0),15` flood-fill is a **read-scan**, not a
  write loop — the hot inner loop is:
  ```
  26 8a 04   MOV AL, ES:[SI]   ; read a pixel from A0000 (this faults)
  0a c0      OR  AL, AL        ; test
  75 03      JNZ +3            ; branch on the result
  4f         DEC DI
  75 f4      JNZ -12           ; loop back
  ```
  So every pixel *read* faults (→ a V86 round-trip), and a full-screen flood scans the whole screen →
  the demo never finishes its first paint. **Implication for the fast path:** batching writes alone
  isn't enough — the fast path must be a small **flags-accurate** in-host interpreter that runs the
  inner loop (loads + stores to A0000, `OR/CMP/TEST`, `INC/DEC`, `Jcc`/`LOOP`) until execution leaves
  A0000, then hands control back to V86. It must STOP (return to V86) on any opcode it doesn't fully
  model so it can never derail the guest. Sizable + flag-exact → deserves a focused pass. (Self-note: a
  diagnostic `memlog` with `b[128]` + 8-digit `zhex` per byte overflowed the stack and crashed the
  host — `zhex` writes a full DWORD; use a 2-digit byte formatter and a 160+ byte buffer.)

## Driving the VM headless (`scripts/qmp.py`)
Wrote a small QMP client (screendump / cd hot-swap / send-key / type / click / drag). Lessons that
cost time: QMP `send-key` drops keys on long strings (use ≥0.15s spacing; forward-slash paths avoid
the backslash-qcode issue); `ctrl`-combos are unreliable; **window focus is the hard part** — the
reliable primitives are *taskbar-button click to raise/focus a window* then Alt+F4, and *Alt+Space→N*
to minimise. Also: `pgrep -f qemu-system` in a wait-loop matches the loop's own command line — use
`pgrep -x qemu-system-x86_64`. `RUNTEST.BAT` now auto-opens the log in Notepad and re-copies the host
per run (`tools/dostest/runtest-demos.bat`).

## Gotchas reaffirmed
- **I/O traps are event 0**, not the disasm's event 2 (already in `vdm-host-test-harness` memory).
- **CD caching:** XP caches the CD; a QMP hot-swap isn't seen until re-read — eject(force) → wait →
  change-medium with a NEW label → in-guest re-open D:; reboot is the 100% fallback. Verify bytes in
  both `build/` and `vm/test.iso` when a change "doesn't show".
