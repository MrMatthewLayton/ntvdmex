# 2026-06-01

Project kickoff. Read NTVDMEX.md, ran the feasibility discussion, made foundational scoping
decisions, and stood up the `docs/` scaffold.

## Done

  (see research/signing-and-wfp.md).
- Recorded 5 ADRs (0001–0005); 0004 left **Proposed** pending Spike-001.
- Wrote roadmap (M0–M8), risk register, glossary, and research notes.
- Defined Spike-001 (the make-or-break V86 keystone test).

## Learned
- `[FACT]` Real NTVDM already uses V86 on x86 — software emulation was only for non-x86 NT and
  64-bit Windows. So the "no CPU emulation" premise is native to XP-32, not exotic.
- `[FACT]` XP-32 does not verify usermode EXE signatures, and kernel DSE is Vista-x64+. Signing
  is therefore *not* the blocker. WFP is — and we sidestep it via the WOW registry repoint.
- `[FACT]` (user correction) **ReactOS NTVDM uses Fast486 software emulation, not V86.** So it
  is a reference for DOS/VDD/WOW logic but proves nothing about the `NtVdmControl`/V86 path.
- `[FACT]` Linux **dosemu** (V86 via `vm86()`) is the closest architectural analog to what we
  want — usermode host + kernel V86 + trap-and-reflect.

## Decided
- Scope = DOS + Win16, Win16 deferred behind a seam (ADR-0003).
- Target VM **and** bare metal, VM-first dev loop (ADR-0005).
- Anchor on reusing the kernel VDM via `NtVdmControl`, pending Spike-001 (ADR-0004).

## Surprises / dead-ends
- The "signed system file" worry turned out to be a non-issue; the genuine risk moved to a
  completely different place — whether a third-party host can drive the *kernel's* VDM at all,
  which no open project demonstrates.
