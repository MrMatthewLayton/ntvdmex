# 2026-06-02

Stood up the build system and shipped the first runnable artifact: a Luna-themed DOS-style
shell preview (non-interactive). Goal was to lock the toolchain and the window/console shell
before the hard V86 work.

## Done
- Chose and wired the build toolchain: **CMake + mingw-w64 `i686-w64-mingw32`** cross-compiler,
  driven from macOS. Toolchain file `cmake/toolchain-xp32-mingw.cmake`; `CMakeLists.txt` hard-fails
  on a non-32-bit/non-Windows target. → **ADR-0006**.
- Wrote the shell preview (`src/`): fixed **80×25** text console (OEM raster font, light-gray on
  black, blinking cursor) in a fixed-size window whose Luna frame comes from a Common-Controls 6.0
  **manifest** — no custom theming code. The command-line is intentionally **non-functional**.
  - `main.c` (window/loop/blink), `console.c/.h` (grid model + GDI paint), `runtime.c` (no-CRT
    entry + `mem*`).
- Verified build correctness on the host: valid **PE32 GUI i386**, imports **only**
  kernel32/user32/gdi32/comctl32, subsystem/OS version **5.01**, manifest embedded, ~20 KB,
  standalone. Added `scripts/build.sh` and `.gitignore`.
- Documented: ADR-0006, `research/build-toolchain.md`, updated ROADMAP (M0 toolchain + shell
  boxes), STATE, and index READMEs.

## Learned
- `[FACT]` (reproduced) The Homebrew `mingw-w64` is **UCRT-default**: an ordinary link imports
  eight `api-ms-win-crt-*.dll`. **UCRT is not on XP**, so such a binary won't load there.
- `[FACT]` Linking **`-nostdlib`** (own entry `WinMainCRTStartup` + own `mem*`) reduces the import
  table to Win32-only DLLs that ship with XP — the clean, toolchain-independent fix.
- `[FACT]` GCC rewrites a hand-written `memset`/`memcpy` loop into a call to itself at `-O2`;
  guard the definitions with `-fno-builtin -fno-tree-loop-distribute-patterns`.
- `[FACT]` XP's loader checks PE subsystem/OS-version stamps; pin them to **5.01** at link time.
- `[FACT]` The "Luna look" needs **zero** theming code — the Common-Controls 6.0 manifest opts the
  process into uxtheme and the standard frame renders as Luna on a themed XP box.

## Decided
- **ADR-0006** — build with mingw-w64 (i686) cross-compiler, **no C runtime**. *Accepted.*
- Shell-first MVP: get the window/console shell correct now; it becomes the render sink the
  V86/DOS core feeds later (M2/M3).

## Surprises / dead-ends
- Expected "just cross-compile and ship"; the UCRT-default trap meant the *first* clean build
  would have silently failed to load on XP. Caught it by inspecting the import table rather than
  trusting a successful link.
- Can't eyeball the GUI on macOS (no Wine) — build correctness is verifiable here, the *visual*
  result is not. Deferred to the XP VM.

## Update — first XP run failed: "application configuration is incorrect"
- `[FACT]` That message is the SxS activation error (`ERROR_SXS_CANT_GEN_ACTCTX`). Our embedded
  manifest carried a multi-line **XML comment in the prolog** (between `<?xml?>` and `<assembly>`).
  XP's `sxs.dll` (v5.1) is stricter than Vista+/7 and fails activation on that — later Windows
  tolerates it, which is why such manifests "work on my machine" but not on XP.
- Fix: reduced `res/ntvdmex.manifest` to the **canonical, comment-free** MS Common-Controls 6.0
  form; moved the prose into `res/ntvdmex.rc` (windres strips `.rc` comments). Added a
  `NTVDMEX_EMBED_MANIFEST` CMake option (default ON) to build a no-manifest diagnostic variant.
  Rebuilt; verified the embedded manifest is clean and imports stay XP-only. **Awaiting re-test
  on the VM.**

## Update — Spike-002 Run 1: in-session repoint ignored
- `[FACT]` Repointed `Control\WOW\cmdline` and launched `dosstub.com` in the same session →
  **stock `ntvdm.exe` ran, our probe didn't.** The `.COM` *did* trigger a VDM support process, so
  the trigger/routing work — only the redirection had no effect.
- `[BELIEF]` Most likely the HKLM write didn't apply (admin needed) or the WOW command lines are
  **boot-cached** by `csrss`/`basesrv` (read into static server data at boot). → Run 2: set value,
  confirm with `reg query`, **reboot**, retry.
- `[BELIEF→VERIFY]` If reboot still fails, `cmdline` isn't the DOS launch mechanism on XP;
  disassemble `kernel32!BaseCheckVDM` + `basesrv.dll` to find the real value. Amends ADR-0002.

## Update — local XP test bench (QEMU + HVF)
- Decided to run XP as a local VM to tighten the test loop. This Mac is **Intel Xeon + HVF**
  (`kern.hv_support=1`), so XP runs **hardware-accelerated → real V86** (TCG emulation would
  defeat the project's premise). QEMU 10.2.1 + UTM already installed; chose **raw QEMU** for
  scriptability over the UTM GUI wrapper.
- Wrote `scripts/xp-vm.sh` (install/run/info) configured for **approximately period-correct,
  XP-driverless** hardware: i440FX/PIIX3 + SeaBIOS, `-cpu host` via HVF, 1 GB, IDE qcow2, Cirrus
  GD5446, **Sound Blaster 16** (IRQ5/DMA1,5 — what DOS audio targets), RTL8139 NIC (user NAT +
  host port-forwards 2323→23 etc. for later automation), PS/2 + USB tablet, RTC localtime.
  Validated the full QEMU arg/device line (tcg, CPU halted) — all accepted.
- `[FACT]` Documented the period-correct rationale + the one real tension (modern CPU via HVF vs
  era CPU — we keep real silicon on purpose) in `research/xp-test-vm.md`.
- **Not in git:** ISO + `vm/` disk gitignored; confirmed via `git check-ignore`.

## Update — Spike-002 SUCCESS (interception proven)
- Installed XP SP3 in the QEMU VM, snapshotted it `clean`, ferried binaries in via a `hdiutil`
  transfer ISO (`xp-vm.sh transfer`), and ran the spike.
- `[FACT]` **The Luna shell preview runs on this fresh XP SP3** (observed via QMP screendump).
- `[FACT]` **ADR-0002 confirmed.** After repointing `Control\WOW\cmdline` and **rebooting**,
  launching a 16-bit DOS program ran *our* `wowprobe.exe` as the VDM support process
  (`C:\ntvdmex\wowprobe.log` written).
- `[FACT]` **Boot-cached:** the repoint had no effect in-session (Run 1), only after reboot —
  `csrss`/`basesrv` read the WOW command lines at boot.
- `[FACT]` **No argv:** XP launched us with a bare `"C:\ntvdmex\wowprobe.exe"` — the DOS program
  to run is delivered via the CSRSS/VDM channel, not the command line. `[BELIEF]` real `ntvdm`
  queries CSRSS (BaseSrv VDM LPC) for it; recovering that + `NtVdmControl` is Spike-001's job.
- Dev-loop tooling: drove the VM from the host over a **QMP socket** (`vm/qmp.sock`) added to
  `xp-vm.sh` — used `screendump` to read the guest screen/log directly instead of asking the
  user. Built a 16-bit **MZ `.exe`** trigger (`tools/wowprobe/make-dosexe.sh`) alongside the
  `.COM` (a headerless `.COM` can be rejected as "not a valid Win32 application").
