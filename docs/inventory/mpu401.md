## Headline — UART mode out is right; everything around it is thin

The part every PC game uses, UART-mode output, is modelled properly and pinned by the battery:
the `FFh`/`3Fh` handshake with its `FEh` acknowledge, the active-low status flags, running status,
and realtime bytes arriving in the middle of another message. Doom has driven it end to end —
`midi_msgs=0x2d8` to XP's GS Wavetable synth (`docs/log/sessions/session-21.md:34`), about 750
messages a run (`session-22.md:34`). That is a guest exercising it, not an oracle agreeing with it.

What surrounds it is not modelled: the card never raises an interrupt, nothing ever arrives on
MIDI IN, **System Exclusive is swallowed** and never reaches the synth, and in UART mode we
acknowledge commands the real part ignores. Intelligent mode is declined by design
(`vdd_mpu.h:15-17`), but "declined" here means every intelligent-mode command is **acknowledged
and ignored** — which is itself an answer, and a wrong one.

## Gaps worth closing, in order

1. **System Exclusive never reaches the synth** (§3). Assemble `F0h…F7h` into a buffer and send
   it with `midiOutLongMsg`; cancel running status on sysex and system common as MIDI 1.0 says.
   This is the one gap a listener hears: every GM/GS reset and set-up message is lost today.
2. **The UART-mode command rules** (§2). In UART mode only `FFh` is recognised and it is not
   acknowledged; a reset should leave nothing in the queue but its own ACK. Today every command
   in every mode queues an `FEh`, so the ordinary detection sequence leaves stray bytes behind.
   This is the path every MIDI driver's detection runs through.
3. **No interrupt and no MIDI IN** (§1, §4). Raise the configured IRQ while DSR is low (ACKs
   included), and decide the IRQ number with the environment (`P330` in `BLASTER`, and the IRQ an
   SB16 driver will look for). MIDI IN from a host `midiIn` device follows from the same queue.
4. **Intelligent mode** (§2). Declined in `vdd_mpu.h:15-17`, but ACK-and-ignore is not declining —
   it is claiming the commands worked. At minimum the request commands (`ACh`, `ADh`) should return
   their data byte; the full sequencer is its own piece of work and should be decided on the spec,
   not on whether a shelf guest asks.
5. **DRR is never busy** (§1). Model the busy window after a reset.
6. **A probe and an oracle.** Nothing here has been compared with a machine. A `p_mpu` probe
   (status at rest, `FFh` then read, `FFh` in UART mode, `3Fh` twice, `ACh`) run on the four
   oracles would settle items 2, 4 and 5 against a real answer rather than this reading of the
   manual.
